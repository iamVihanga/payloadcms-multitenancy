Part A

Foundation

A running Payload instance with Postgres, a super admin account and the folder layout the rest of the guide assumes. About an hour, most of it waiting on installs.

01Prerequisites and ground rules

Goal: know what you are building, and have Node, pnpm and Postgres ready.

This guide builds one thing: a property marketplace where you run the platform, businesses list properties from their own subdomain site, and anyone can browse every published listing from the main domain. Work through it in order — each step assumes the one before it.

The companion architecture guide explains why each piece looks the way it does. This one only explains what to type. Where a decision needs justifying, there is a link to the relevant chapter.

What you need installed

ToolVersionNote
Node.js20.9+ or 22+Payload 3 targets modern Node. Check with node -v.
pnpm9+npm and yarn work too; every command below has a pnpm form.
PostgreSQL14+Local install, Docker, or a hosted database. One empty database is enough.
A domain—Only needed at step 24. Everything before that runs on localhost.

Decisions this guide has already made for you

  • Postgres, not Mongo. Tenant scoping is a foreign key and a compound unique index; a relational database is the natural fit.
  • Two auth collections. users for you and business owners, customers for the public. The reasoning is in the architecture guide.
  • Subdomains, not paths. villa-lanka.marketplace.lk rather than marketplace.lk/villa-lanka. Custom domains come later and reuse the same resolver.
  • Businesses use the Payload admin panel at first. Swapping in a custom dashboard later changes no access rules.

Names used throughout

Substitute your own domain wherever marketplace.lk appears. Everything else can stay as written.

Part B

Tenancy core

The three pieces that make a tenant real: a Tenants collection, membership on users, and the plugin that ties them together. By the end of this part two businesses exist and neither can see the other.

05Access helpers

Goal: isSuperAdmin, role-aware tenant lookup and the reserved-name list, ready to import.

  • src/access/isSuperAdmin.ts
  • src/utilities/getUserTenantIDs.ts
  • src/utilities/extractID.ts
  • src/lib/reserved.ts

Three small files that every access rule from here on imports. Write them first and the rest of the guide reads cleanly.

One more: the reserved subdomain list, in its own module because both a validation hook and the middleware will import it. Two copies of this list will drift, and the failure mode is a business owning api.marketplace.lk.

Note the type error on user.tenants until step 8 — the field does not exist yet. It will resolve once the plugin is wired and you regenerate types.

06The Tenants collection

Goal: a business record with a validated subdomain, and a hard line between owner-editable and platform-only fields.

  • src/collections/Tenants/index.ts
  • access/tenantAdminUpdate.ts
  • hooks/validateSubdomain.ts

A tenant is a business. The plugin never defines these fields — every one of them is yours, and the split that matters is between what a business may edit about itself and what only you may change.

Why status and plan are field-locked

A business owner can edit their own tenant document — that is how they change their tagline and contact details. Without the field-level access.update on status and plan, the same request could also flip them from pending to active, or from free to pro.

The brand.logo upload field is deliberately missing: media becomes tenant-scoped in step 10, and adding the relationship before then creates a circular ordering problem. You add it at the end of that step.

07The Users collection

Goal: staff and business owners in one collection, with membership rows that carry a role.

  • src/collections/Users/index.ts
  • access/create.ts
  • access/read.ts
  • access/updateAndDelete.ts
  • access/isAccessingSelf.ts

Replace the generated src/collections/Users.ts with a folder. Four access files, then the collection itself.

Now the collection. The membership array comes from the plugin's tenantsArrayField export so you can attach a role to each row — the default field has no roles.

The single most important line

access: { update: ({ req }) => isSuperAdmin(req.user) } on the roles field. Without it, any business owner can PATCH their own user document and become a platform admin. Field-level access is what stops it — collection-level update already allows them to edit themselves.

Three lines doing the heavy lifting

admin.user: 'users' tells the plugin which collection carries membership. userHasAccessToAllTenants is the only thing that lets anyone see across tenants. debug: true reveals the injected tenant field in the panel while you build — watching which document lands in which tenant teaches the model faster than reading about it.

09Bootstrap and prove isolation

Goal: you are a super admin, two businesses exist with one owner each, and neither owner can reach the other.

  • src/seed/bootstrap.ts

There is a chicken-and-egg problem here worth naming: the roles field can only be updated by a super admin, and you are not one yet. No amount of clicking in the panel will fix that. Bootstrap it with a script instead, which also creates two businesses to test isolation against.

Now verify the isolation by hand — this is the first moment the whole model is testable:

  1. Log in as owner@villalanka.test. The tenant selector shows Villa Lanka only.
  2. The Tenants list shows one row. The Users list shows one user.
  3. Log in as yourself. The selector lists both businesses and switching filters the panel.
  4. As the Villa Lanka owner, request the other tenant by ID directly and confirm the refusal:
Checkpoint — Part B
  • You hold super-admin and see both businesses in the tenant selector.
  • Each owner sees exactly one business and one user.
  • A PATCH from one owner to the other's tenant is refused.
  • Regenerating types produces a tenants array on the User interface.
If an owner sees an empty panel

Their tenants array is empty, or its rows have no tenant set. A user in the admin collection with no membership is denied every tenant-scoped operation by design — check the sidebar on their user document before debugging anything else.

14Verify the boundary

Goal: proof, before any UI exists, that a business cannot read or write another's data.

Everything through part C is backend. Before building any UI, confirm the boundary holds — a bug found here costs minutes, the same bug found after the frontend exists costs an afternoon.

In the panel

  1. As the Villa Lanka owner, the Properties list shows only their two listings.
  2. Creating a property auto-fills the tenant (visible because debug is on) and never offers the other business.
  3. Saving a second listing with the slug misty-cabin inside the same business fails with your validation message.
  4. Both businesses owning a misty-cabin is fine.

Over the API

Checkpoint — Part C
  • Anonymous reads return published listings only, and never a draft.
  • Each owner's property list contains only their own documents.
  • A cross-tenant PATCH is refused.
  • The same slug exists under both businesses without conflict.

If an anonymous read returns drafts, canReadProperty is returning true for everyone — the plugin adds no constraint for unauthenticated requests. Architecture guide §5.2 has the table of who gets filtered.

Part D

The public marketplace

The apex domain: anyone can browse every published listing from every active business, filter it, and click through to a detail page. All of it anonymous, so all of it leaning on the access rules from part C.

And the query layer. Keeping every find in one module is what stops overrideAccess: false being forgotten on the twelfth page you write:

The two arguments that matter

overrideAccess: false turns the rules on; user says who is asking. Pass the first without the second and every request evaluates as anonymous — which is safe but breaks anything personalised. Pass neither and Payload happily returns drafts to the public.

16Browse every listing

Goal: a filterable, paginated marketplace page reading across all active businesses.

  • src/app/(marketplace)/properties/page.tsx

The browse page: filters in the URL, results from the query layer. No tenant anywhere — this is the cross-business view.

depth: 1 is what makes property.tenant a populated object rather than an ID — that single setting is why each card can name the business that listed it without a second query per row. Rendering 24 cards that each fetch their own tenant is the classic multi-tenant slowdown.

17The detail page

Goal: a per-listing page keyed by business and slug, linking through to the business's own site.

  • src/app/(marketplace)/properties/[tenantSlug]/[slug]/page.tsx

The detail page is keyed by both the business and the listing, because two businesses may share a slug. That URL shape is a direct consequence of the per-tenant uniqueness rule from step 12.

Checkpoint — Part D
  • /properties lists published listings from both businesses.
  • No draft appears, in any filter combination.
  • Suspending a tenant in the panel removes its listings from the marketplace immediately.
  • A detail page renders and links out to that business's subdomain (which 404s until part E).
Part E

Tenant sites

One deployment, many hostnames. Middleware splits the host, a layout resolves the business, and every page below it is scoped to one tenant without a single extra deployment.

18Middleware and hostnames

Goal: villa-lanka.localhost:3000 rewrites to /sites/villa-lanka, and reserved names never do.

  • src/middleware.ts

Middleware runs on the edge runtime, where you cannot open a database connection or import Payload. So it does string work only: split the hostname, rewrite the path. The tenant is resolved one layer down, in step 19.

Testing subdomains locally

With NEXT_PUBLIC_ROOT_DOMAIN=localhost, subdomains of localhost work with no setup in Chrome and Firefox:

Leave COOKIE_DOMAIN empty in development

Browsers reject a Domain attribute on localhost. Set it and the login cookie is silently dropped, which looks exactly like a broken auth setup. In production it becomes .marketplace.lk so one session covers the panel and every subdomain.

23Self-serve business signup

Goal: a public endpoint that creates a business and its first owner atomically, in a pending state.

  • src/collections/Tenants/endpoints/registerBusiness.ts

Until now you created businesses with a script. Self-serve signup is the one flow the plugin cannot help with: the tenant does not exist yet, so there is no membership to authorise against. A custom endpoint wrapped in a transaction keeps the two writes atomic.

This is your most exposed surface

Payload does not authenticate custom endpoints — this one is deliberately public. Rate-limit it, keep status: 'pending' so a new business cannot go live without you, and never let the body decide roles, status or plan. The whitelist at the top of the handler is the entire defence.

24Ship it

Goal: migrations instead of push, wildcard DNS and certificates, and a verified production deploy.

  • src/migrations/
  • .env.production
  • src/payload.config.ts

Switch from push to migrations

In development the Postgres adapter pushes schema changes straight into the database. Production must not work that way. Generate a migration from your current schema, commit it, and run migrations as part of the build:

DNS and certificates

  • An A record for marketplace.lk and a wildcard *.marketplace.lk, both pointing at the same server.
  • A wildcard TLS certificate. Let's Encrypt only issues wildcards over the DNS-01 challenge, so your reverse proxy needs API credentials for your DNS provider. This is the step that most often stalls a first subdomain deploy — test it before you need it.
  • One container serves everything. No per-tenant deploys, no per-tenant environment variables.

After the first deploy

Checkpoint — production
  • https://marketplace.lk and https://villa-lanka.marketplace.lk both serve, on valid certificates.
  • Logging in at /admin keeps you logged in on a subdomain (the cookie domain works).
  • An anonymous GET /api/properties returns no drafts.
  • A reserved name such as api.marketplace.lk redirects rather than resolving a tenant.
  • Deleting a test tenant removes its listings — confirming cleanupAfterTenantDelete behaves as expected.

What comes after

  • Custom domains. The resolver already accepts one; what is missing is on-demand certificate issuance and a verification flow so a business proves it owns the domain.
  • Plan limits. A beforeChange hook on properties that counts existing listings and refuses past the free-tier ceiling.
  • Templates. The template select from step 20, mapped to real layout components.
  • A mobile client. Native apps cannot rely on the host header, so tenant scope becomes an explicit query parameter against the same REST API — no new endpoints needed.
  • Tests. Seed two tenants and assert the failures: tenant A reading, updating and deleting tenant B's documents. Multi-tenant bugs are invisible in single-tenant testing.

Before adding users, walk the security checklist in the architecture guide. Most items are one line of config, and each closes a path the plugin does not close for you.
