01The mental model

Before any code: Payload multi-tenancy is not a separate runtime, a separate database or a separate deployment per business. It is one Payload instance, one database, and a tenant relationship field on every document that belongs to someone. Everything else — the admin tenant selector, the list filtering, the access rules — exists to make sure a query never crosses that column without permission.

The shape of it

Three collections carry the whole model:

  • Tenants — one document per business. You define its fields; the plugin never dictates them. This is where slug (the subdomain), domain, plan, status and branding live.
  • Users — your admin-panel auth collection. The plugin adds an array field to it: which tenants does this user belong to, and with what role in each. A user can belong to several.
  • Tenant-scoped collections — properties, media, per-tenant settings. The plugin adds a tenant relationship field to each one you list, and wraps their access functions.

What the plugin gives you

  • A tenant relationship field on every collection you list, hidden from the UI unless debug: true.
  • A tenant selector in the admin nav, backed by a payload-tenant cookie.
  • A base filter so list views, relationship pickers and Lexical internal links only show the selected tenant's documents.
  • Automatic tenant assignment on create, taken from the selected tenant.
  • isGlobal: true collections — one document per tenant, edited as if it were a global.
  • An access wrapper around every create, read, update, delete, readVersions and unlock function on those collections.
  • Cleanup of tenant-owned documents when a tenant is deleted (on by default).

What it leaves entirely to you

ConcernPluginWhat you write
Roles inside a tenantnoThe roles select on the tenants array row, plus the access functions that read it.

The payload-tenant cookie

The tenant selector writes the selected tenant ID into a cookie named payload-tenant. This cookie drives the admin list filters, and you can read it inside your own access functions and hooks:

Read this once and remember it

The cookie is a view preference, not a permission. It narrows what an already-authorised user is looking at. Never treat "the cookie says tenant X" as proof that the user may write to tenant X — always check membership through the user's tenants array.

Where your existing plan fits

Everything in this guide assumes Payload owns the collections it is filtering. If part of your domain data lives outside Payload — in a Drizzle schema you control directly, for example — the plugin's access wrapper does not protect it, and every tenant constraint on that side has to be written by hand in your own queries. Pick one owner per table before you build; splitting a single collection across both is where multi-tenant bugs hide.

02Mapping your three user types

Your three user types are not three roles. Two of them are staff-like and belong in the admin-panel auth collection; the third is a customer of the marketplace and belongs somewhere else entirely.

WhoCollectionRoleLogs in atCan
Platform admin
you and your team		usersroles: ['super-admin']/adminEverything, across every tenant. Creates and suspends tenants.
Business user
owner of a listing business		userstenants[]: { tenant, roles: ['tenant-admin'] }/adminCreate and manage properties for their own tenant. Invite staff into that tenant.
Normal user
someone browsing		customersnonethe public siteBrowse every published property, save favourites, send enquiries. No admin panel.

Why the public user gets its own collection

This is the decision that shapes everything downstream, so it is worth being explicit about the trade-off.

Recommended

Two auth collections

users for staff and businesses, customers for the public.

  • The admin panel only ever knows about users, so a customer signup can never become an admin-panel account by mistake.
  • Customers need none of the tenant machinery — no tenants array, no roles, no tenant selector.
  • Different auth settings per audience: email verification and lockouts for customers, stricter token expiry for staff.
  • Sessions are separate. A person can be a business owner and a browsing customer without the two colliding.

One collection, role-gated

Everyone in users, with access.admin refusing panel entry to customers.

  • Fewer collections, one login form, one password-reset flow.
  • But: every customer document carries staff-only fields, and one mistake in access.admin exposes the panel.
  • The plugin's tenant constraint applies to this collection — a customer with zero tenants gets false on tenant-scoped reads, which you then have to override.
  • Reasonable only if customer accounts are a thin afterthought.

The rule that makes this work

Inside the plugin, the automatic tenant constraint is applied only when all of these are true:

  • there is a req.user,
  • that user's collection is the one set as admin.user,
  • and userHasAccessToAllTenants(user) returns false.

So a logged-in customer is never tenant-constrained by the plugin, and neither is an anonymous visitor. That is exactly what you want for public browsing — and exactly why the public read rules are yours to write.

Consequence

A user in the users collection with an empty tenants array gets false on every tenant-scoped operation — except their own user document. Plan your invite flow so a business user is created with their tenant already attached, otherwise their first login shows an empty panel.

Two roles cover the realistic cases; add more only when a customer asks. These live on each row of the user's tenants array, not at the top level:

03The data model

Deciding which collections get a tenant field is the other half of the design. Get it wrong in one direction and businesses share data they shouldn't; get it wrong in the other and every business ends up maintaining its own duplicate list of amenities.

CollectionTenant-scopedWhy
propertiesyesThe core owned object. One business's listings, invisible to another in the panel.
mediayesPhotos are owned. Without this, one business browses another's uploads in the file picker.
site-settingsyes globalOne document per tenant: hero copy, theme, contact block for their subdomain site.
enquiriesyesCreated by the public, read only by the business the property belongs to.
property-types, amenities, districtsnoShared taxonomy. Marketplace-wide filtering only works if every business uses the same terms.
tenantsnoIt is the tenant. The plugin adds its own access constraints here.
usersvia arrayMembership lives on the user, not a single tenant field. A user can belong to several.
customersnoBelongs to the marketplace, not to any business.
A rule of thumb

If two businesses would ever want different values for the same row, it is tenant-scoped. If the marketplace needs to filter across all businesses using it, it is shared. Amenities are shared; the property that has them is not.

The tenants collection

The plugin never defines these fields — you do. Notice the split between what a business may edit about itself and what only you may change.

Deleting a tenant deletes its documents

cleanupAfterTenantDelete defaults to true: removing a tenant removes every document carrying its ID and strips it from users. That is usually what you want, and it is also why delete on this collection is super-admin only. For churn, prefer status: 'suspended' — it is reversible.

The properties collection

The tenant field is not written here — the plugin injects it. What you write is everything that makes a listing, plus the hook that keeps slugs unique per tenant rather than globally.

Uniqueness, per tenant

A unique: true field is unique across the whole table, which would mean the first business to claim misty-cabin takes it from everyone. Two ways out, and they compose:

  1. A beforeValidate field hook that queries for the same slug within the same tenant and throws a readable ValidationError. This is what the official example does, and it produces a good message in the admin UI.
  2. A compound index on the collection, with disableUnique on the field, so the database enforces it too. Belt and braces — the hook races under concurrent writes, the index does not.

One document per tenant

Each business needs exactly one settings document for their subdomain site. Payload globals are single-instance, so the plugin gives you isGlobal: true: a normal collection that behaves like a global within the selected tenant.

Media is easy to forget

If media is not tenant-scoped, every upload field in the panel shows every business's photos. Scope it, and give the collection a staticDir or storage prefix per tenant if you also want them physically separated on disk or in object storage.

The membership field, with roles

Setting includeDefaultField: false means you place the array yourself — which is the only way to attach a role to each membership row.

The one field you must lock down

Field-level access.update on roles is what stops a business user granting themselves super-admin by POSTing to their own user document. The plugin locks the membership array itself to super admins by default; if you widen that with arrayFieldAccess, you are also deciding who can grant tenant membership.

05Access control, precisely

This is the chapter to read twice. The plugin does not replace your access functions — it wraps them, and the composition rule decides whether a request is tenant-scoped at all.

How the wrapper composes

For every tenant-scoped collection, each of create, read, update, delete, readVersions and unlock is replaced by a wrapped version that runs this sequence:

Who actually gets filtered

RequestTenant filter applied?What protects the data
Anonymous visitor on the marketplacenoOnly the Where your read returns.
Logged-in customernoSame — different collection, so the wrapper skips them.
Business user in /adminyesPlugin constraint AND your rules.
Super adminnoYour rules alone — userHasAccessToAllTenants opts them out.
Server-side Local API callnoNothing. Access is skipped unless you pass overrideAccess: false.
The mistake that leaks data

Three of those five rows are not protected by the plugin at all. Every query your Next.js pages make on behalf of the public is one of them. If a page renders a tenant's listings, your query must carry the tenant constraint — the plugin will not add it for you.

Access for properties

Note the asymmetry: read returns true for staff and lets the plugin narrow it, while update returns an explicit { tenant: { in: ... } }. That is deliberate — membership alone is enough to see a tenant's listings, but only the tenant-admin role may change them, and the plugin's constraint knows nothing about roles.

Don't lean on filterOptions for security

The plugin's tenant field carries filterOptions limiting the dropdown to the user's tenants — but it also ships a custom validate, and Payload only validates filterOptions when the default relationship validator is called from your own validate function. Treat it as a UI convenience. The server-side guard is your create check above, or a beforeValidate hook that forces the tenant.

Forcing the tenant on API writes

Anything created outside the admin panel — a mobile app, a custom dashboard form, a seeding script — arrives without the selected-tenant cookie. Rather than trusting the client to send the right tenant, derive it:

Public writes: enquiries

Enquiries invert the usual direction — the public creates them, the business reads them. The tenant is copied from the property server-side so the submitter cannot address someone else's inbox.

overrideAccess, the one-line footgun

Local API calls skip access control by default. That is correct for trusted server work and wrong for anything that renders on behalf of a visitor:

Pass overrideAccess: false together with user. Without user, the call is evaluated as anonymous even if someone is signed in.

06Subdomains and routing

The plugin has no opinion about URLs. Everything in this chapter is plain Next.js: one deployment answering for the apex domain, every business subdomain, and the admin panel.

URLServesQuery scope
marketplace.lkThe public marketplaceEvery published property from every active tenant
villa-lanka.marketplace.lkOne business's own sitetenant.slug = villa-lanka, published only
marketplace.lk/adminPayload panelWhatever the signed-in user's membership allows
marketplace.lk/api/*REST & GraphQLAccess control, every time

DNS and certificates

  • An A record for marketplace.lk and a wildcard *.marketplace.lk pointing at the same server.
  • A wildcard TLS certificate. Let's Encrypt only issues wildcards over the DNS-01 challenge, so the reverse proxy needs API credentials for your DNS provider — this is a one-time setup and the usual place where the first subdomain deploy stalls.
  • Everything behind it is one container. No per-tenant deploys, no per-tenant environment variables.

Middleware, not rewrites

The docs show a next.config rewrite using a host pattern. It works, but middleware gives you reserved-name handling, custom domains later, and a readable fallback in one place.

Why the middleware only does string work

Middleware runs on the edge runtime, where you cannot open a database connection or import Payload. So it splits the host and rewrites — nothing more. The tenant is resolved one layer down, in the route's layout, which runs in Node.

A slug is a piece of infrastructure, not just a field. Validate it at the point of entry:

Keep the reserved list in one module and import it into both the hook and the middleware. Two copies will drift, and the failure mode is a business owning api.marketplace.lk.

Local development

  • villa-lanka.localhost:3000 resolves in Chrome and Firefox with no setup. Set NEXT_PUBLIC_ROOT_DOMAIN=localhost.
  • lvh.me and *.lvh.me both point at 127.0.0.1 publicly, which helps when testing on a phone or in Safari.
  • Leave auth.cookies.domain unset in development — browsers reject a Domain attribute on localhost, and you will be silently logged out on every subdomain hop.

One session across every subdomain

Payload's auth cookie is set for the host that issued it. Without a domain attribute, logging in at marketplace.lk/admin leaves you anonymous on villa-lanka.marketplace.lk. Setting cookies.domain to .marketplace.lk shares the session across all of them — which is what you want here, since the panel and the tenant sites are the same application.

The same applies to csrf: list every origin that will send authenticated requests. It takes a fixed array, not a wildcard, so for many subdomains either front them with a single origin or generate the list at boot from active tenants.

07The admin panel for businesses

Business users logging into the same panel you use is the fastest thing to ship and the easiest to get subtly wrong. Two questions decide the shape: what do they see, and how did they get there.

What a business user sees

With the config from §4, a user holding one membership gets a panel where the tenant selector shows only their business, list views are already filtered, and relationship pickers offer only their own documents. What they should not see is the platform's furniture:

Hidden is cosmetic

admin.hidden removes a collection from the nav and admin routing. It does not stop a request to /api/property-types. Access control is the security boundary; hidden only tidies the interface. Write both.

Payload panel, or your own dashboard?

Start here

Give them the Payload panel

  • Zero frontend to build. Drafts, versions, image uploads and validation all work on day one.
  • The tenant selector, list filters and relationship scoping come from the plugin.
  • Cost: it looks like a CMS, and your branding options are limited to the white-label settings.
  • Good enough for a first paying cohort, and it defers the decision cheaply.

A custom dashboard in Next.js

  • Your UI, your onboarding, your upsell surfaces — and the same look as the marketplace.
  • Talks to Payload through the Local API in server actions, always with overrideAccess: false and the signed-in user.
  • Cost: you rebuild file upload, validation feedback, draft states and pagination.
  • Worth it once the panel's vocabulary starts confusing non-technical owners.

Whichever you choose, the access rules are identical — that is the point of putting them in the collection config rather than in a route handler.

Creating a business and its first owner

Signup is the one flow the plugin cannot help with: the tenant does not exist yet, so there is no membership to authorise against. A custom endpoint, wrapped in a transaction, keeps the two writes atomic:

Custom endpoints are not authenticated

Payload does not guard your endpoints for you. This one is deliberately public, which makes it the highest-risk surface in the app: rate-limit it, require a verified email before status can move to active, and never let the request body set roles, status or plan. Pick the fields you accept explicitly — never spread the body into data.

Inviting staff into an existing tenant

Adding a second user to a business is an ordinary users create, and the access function from §4 already covers it: a tenant-admin may create a user as long as every tenant named in the new user's membership array is one they administer. What stops privilege escalation is the field-level rule on roles — a tenant-admin can invite a colleague, but cannot mint a super admin.

08Reading it back

Two surfaces read the same table with different scopes: the marketplace reads across every active tenant, a business site reads exactly one. Both are anonymous, so both depend entirely on the rules in §5.

Across every business

With depth: 1 each result carries its tenant object, which is what lets a marketplace card link back to {tenant.slug}.marketplace.lk/properties/{slug}. That cross-link is the whole point of running both surfaces from one database.

Within one business

Constrain by the tenant ID you already resolved, not by the slug from the URL. The layout has verified the tenant exists and is active; re-querying by slug invites a mismatch between what the header says and what the list shows.

Keeping it fast

  • Indexes. The plugin indexes tenant. Add your own on slug, district and anything you sort by; a compound [tenant, slug] index serves both uniqueness and lookup.
  • Depth costs joins. depth: 1 is usually right for cards; use depth: 0 plus a select for counts and sitemaps.
  • Cache per tenant, invalidate per tenant. Tag cached reads tenant:{slug} and call revalidateTag from an afterChange hook on properties, so one business publishing never busts another's cache.
  • Static where it pays. generateStaticParams over active tenants pre-renders every business home page; listing pages that take filters stay dynamic.
  • Watch the N+1. Rendering 24 cards that each fetch their tenant separately is the classic multi-tenant slowdown. One find with depth: 1 does it in a single round trip.

If a mobile app reads the same data

Native clients cannot rely on the host header, so tenant scope has to be explicit: pass the tenant as a query parameter and let the same access rules do the work. Payload's REST API already returns exactly what an anonymous request may see, so GET /api/properties?where[tenant.slug][equals]=villa-lanka needs no new endpoint. Add the app's origin to cors, and prefer a read-only token or plain anonymous reads over shipping anything that can write.

09Security checklist

Work down this before the first business other than you has an account. Most items are one line of config; each one closes a path that the plugin does not close for you.

  • Every tenant-scoped collection is listed in the plugin's collections map — including media.
  • userHasAccessToAllTenants is wired to your isSuperAdmin, and nothing else grants cross-tenant access.
  • Field-level access.update locks roles, status and plan to super admins.
  • No access function trusts the payload-tenant cookie as proof of membership.
  • create access checks req.data.tenant against the user's memberships, or a beforeValidate hook forces it.
  • Every public-facing query passes overrideAccess: false and user.
  • Public read returns a Where that requires both a published status and an active tenant.
  • Enquiries copy their tenant from the referenced property, never from the request body.
  • Custom endpoints validate their own auth — Payload does not.
  • The onboarding endpoint whitelists the fields it accepts instead of spreading the request body.
  • Reserved subdomains are refused by the slug hook, and the same list is used in middleware.
  • auth.cookies.domain is set for production and unset for localhost.
  • cors and csrf list only origins you control.
  • GraphQL is disabled if you are not using it, so it isn't a second unreviewed surface.
  • Tenant deletion is super-admin only, and churn uses status: 'suspended' instead.
  • A test exists that logs in as tenant A and fails to read, update and delete a document belonging to tenant B.
The last item is the one that matters

Multi-tenant bugs are invisible in single-tenant testing — everything looks right until the second business signs up. Seed two tenants with two users in your test setup and assert the failures, not just the successes. It is the only check that catches a regression six months from now.
